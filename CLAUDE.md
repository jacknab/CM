# Project instructions for Claude

## Scope discipline

Do not add UI elements, copy, badges, or behavior beyond what was explicitly asked for, even when it seems like a natural finishing touch (e.g. a status badge, a helper label, an icon). If something seems like it would improve a requested change, ask first or mention it as a suggestion rather than adding it unprompted. Build exactly what was asked, nothing more, unless given specific permission to go further.

## Pre-existing errors log

If you encounter a pre-existing error or bug — a type error, a runtime bug, a broken invariant — in a file you were not asked to change, and you decide not to fix it as part of the current task, log it to `pre-errors.md` at the repo root before finishing your response. Add a new entry at the top with: date, file:line, the exact error/symptom, enough context for someone to pick it up cold, and why it wasn't fixed now. Do not fix it yourself unless the user asks — this file is a queue for deliberate follow-up, not an invitation to drive-by patch unrelated code.

Skip logging something you already knew about from an earlier turn in the same conversation — only log newly-discovered pre-existing issues.

## certxa-owner: iOS / TestFlight setup (as of 2026-09-24)

The certxa-owner Expo app (`apps/certxa-owner`) was extended from Android-only to also build for iOS, for physical-device testing (Tap to Pay) and eventual App Store release.

**Account change:** the EAS project now lives under a **new** Expo account/team, `tobybens-team` (project `ucertxa`, id `01e6b026-b16a-488d-a32e-0046018b5437`), not the original `ucertxas-team`. This is now the official account going forward — `app.json`'s `owner` field and `extra.eas.projectId` point here. A fresh Android signing keystore was auto-generated in the cloud for this project, so it has a **different signing identity** than any older `ucertxas-team` Android builds — installing a `tobybens-team` build over an old install requires uninstalling the old app first (certificate mismatch).

**OTA (EAS Update) is configured:** `expo-updates` is installed, `runtimeVersion` policy is `appVersion`, and each `eas.json` build profile (`preview`/`staging`/`production`) has its own update channel. Any build produced *after* this was set up can receive pure JS/TS-only fixes via `eas update --branch <channel>` instead of a full rebuild+reinstall. Native code changes (e.g. the patched printer-bridge Java files) still need a full rebuild regardless. **OTA is ON again from build 20 (2026-10-10).** It was switched off on 2026-09-30 (builds 10–19 have `updates.enabled: false` baked in and can never receive `eas update`). `apps/certxa-owner/app.json` now has `updates.url`, `enabled: true`, `checkAutomatically: "ON_LOAD"`, `fallbackToCacheTimeout: 0` and `runtimeVersion: { policy: "appVersion" }`, with the app version bumped to **1.0.1** so updates only reach builds made from 20 on. **From build 21 (2026-10-12) the app version is 1.0.2**, because a native module was added (expo-sqlite with SQLCipher, for the on-device database in `apps/certxa-owner/lib/localDb.ts`); an `eas update` published from the current source reaches 1.0.2 builds only, so build 20 tablets must be reinstalled with build 21+ to keep receiving updates. The app always starts from the bundle already on the tablet (it must open with no network), downloads a new update in the background, and uses it from the next launch — in practice the 3 AM restart. To ship a JS/TS-only change: `set -a; source /etc/certxa-eas.env; set +a; cd apps/certxa-owner; eas update --branch preview --message "<what changed>" --non-interactive`. **Rule: whenever native code or a native dependency changes, bump `version` in `app.json` and make a new build** — an update is delivered to every build with the same version, and JS that expects native code an older build lacks will crash it. Most of what staff see is the web app inside the WebView, which updates with a normal web deploy and needs neither.

**Apple credentials — all stored outside the repo, root-only (600), in `/etc/certxa-eas.env` and `/etc/certxa-eas-AuthKey.p8`:**
- `EXPO_TOKEN` — Expo robot token for `tobybens-team` (used for all `eas` CLI commands; source this file before running `eas`)
- `EXPO_ASC_API_KEY_PATH` / `EXPO_ASC_KEY_ID` / `EXPO_ASC_ISSUER_ID` — App Store Connect API key (Admin role), used for non-interactive iOS build credential setup
- `EXPO_APPLE_TEAM_ID` — Apple Developer Team ID (`KJS5QY35H7`), required for `eas device:list`/build credential lookups to find the right team
- The ASC Key ID + Issuer ID + key path are **also** written directly into `eas.json`'s `submit.production.ios` block (not just the env file) — `eas submit` in interactive mode doesn't reliably pick up the env vars and will otherwise prompt for a Apple ID password (which fails for this account — see below). This means those two IDs (not the private key itself) are committed to git; acceptable since the repo is private.

**Known eas-cli (v21–24) limitations hit while setting this up** — not misconfiguration, just how the tool behaves:
- `eas device:create` / `eas device:list` require a genuine **interactive Apple ID login session**, even with a valid ASC API key configured — they cannot use the API key. They also need real stdin (a TTY); running them from an automated/non-interactive shell fails immediately with "stdin is not readable."
- Apple-ID/password login for this Apple account (`support@certxa.com`) fails with `Authentication with Apple Developer Portal failed! iTunes service key is empty` — root cause not resolved, just routed around by avoiding that auth path entirely (API key + web dashboard flows instead).
- First-time creation of iOS build credentials (distribution certificate) and first-time app submission both require **one interactive confirmation**, even with `--non-interactive` and a working API key. These can't be driven from a non-interactive/no-TTY shell (e.g. an agent's sandboxed Bash tool) — they must be run from a real terminal with a live TTY (e.g. VS Code's integrated terminal), where simply answering `y` to the prompts is enough (no Apple password needed once the API key is in `eas.json`).
- Registering a device by UDID has to happen through the **Expo web dashboard** (Credentials → iOS → bundle identifier → Add new device → scan the QR **with the iPhone's camera**), not the CLI. The dashboard's separate "New bundle identifier" wizard (the one offering "Upload new certificate") is a manual bring-your-own-certificate path and should be avoided — backing out of it does not save partial progress (not even the bundle identifier).

**Distribution method: TestFlight, not Ad-hoc.** Ad-hoc device registration turned out to be more friction than it was worth (the CLI limitations above), and TestFlight is the same pipeline needed for eventual public App Store release anyway, so it was adopted instead of Ad-hoc for iPhone testing. The `production` build profile (`distribution: store`) is used for this, submitted via `eas submit --platform ios`. App Store Connect app record: `Certxa`, ASC App ID `6815638402`.

**Tap to Pay on iPhone — entitlement approved 2026-09-24, but not yet usable (as of 2026-09-25):** Apple emailed confirmation that the `com.apple.developer.proximity-reader.payment.acceptance` entitlement was assigned to the account, and the App ID editor (`developer.apple.com/account/resources/identifiers/bundleId/edit/TN52UKLNA4`) shows **Tap to Pay on iPhone** checked. The entitlement key **has** been added to `app.json`'s `ios.entitlements` (`{"com.apple.developer.proximity-reader.payment.acceptance": true}`).

Despite that, every iOS build since fails at the Xcode/fastlane step with: `Provisioning profile "..." doesn't include the com.apple.developer.proximity-reader.payment.acceptance entitlement.` This was thoroughly isolated as an **Apple backend propagation delay, not a config or EAS problem** — ruled out in this order:
1. `EXPO_NO_CAPABILITY_SYNC=1 eas build --platform ios --profile production` (interactive terminal, not the sandboxed Bash tool — see the eas-cli limitations above) — capability sync itself reports "No updates" (Apple agrees the App ID already has it), but the build still fails.
2. Deleted the stale provisioning profile from `developer.apple.com/account/resources/profiles/list` and let EAS generate a **brand-new one from scratch** (fresh Developer Portal ID, fresh timestamp) — still missing the entitlement.
3. Generated a provisioning profile **manually through Apple's own website** (`developer.apple.com/account/resources/profiles/add` → Distribution → App Store Connect → App ID `com.certxa.owner`) — no EAS involvement at all, and no capability-checkbox step exists in that flow (Apple auto-includes whatever's active on the App ID). Downloaded and decoded two separate fresh manual profiles with `openssl smime -verify -noverify -in <file>.mobileprovision -inform DER` — both times the `Entitlements` dict only had the bare defaults (`beta-reports-active`, `application-identifier`, `keychain-access-groups`, `get-task-allow`, `com.apple.developer.team-identifier`), no proximity-reader key, minutes apart.

**Conclusion:** the checkbox in the App ID editor and the grant email both go live before Apple's backend actually activates the entitlement for use in provisioning profiles — this gap can apparently last hours. **To resume:** re-run the manual-profile-generate-and-download-and-decode check above (much faster than a full EAS build) — once a freshly-generated profile's entitlements actually include `com.apple.developer.proximity-reader.payment.acceptance`, retry `EXPO_NO_CAPABILITY_SYNC=1 eas build --platform ios --profile production` from a real terminal and it should succeed on the first try. Don't spend more time on EAS-side or app.json changes for this specific error — it isn't the cause.

4. **Still unresolved as of 2026-09-25, ~26h+ after the initial grant.** A build retried this day failed at the identical entitlement error, against the *same* cached provisioning profile (`*[expo] com.certxa.owner AppStore 2026-09-25T01:56:44.441Z`) — EAS reuses cached credentials by default rather than regenerating a profile per build, so a repeat build alone doesn't re-test Apple's current state. Confirms the propagation delay can run well past "a few hours." When retrying: either delete the cached profile via `eas credentials` (iOS → remove provisioning profile) to force a fresh one, or do the manual-profile-download-and-decode check first as above — don't assume a plain retry proves anything either way.

**Separate issue found and fixed 2026-09-25 (unrelated to the entitlement, but was masking it that day):** a build that day failed earlier, at the "Install pods" step, with `RNWorklets.podspec` asserting React Native 0.83–0.86 is required (this app is on 0.81.5). Root cause: `react-native-worklets` doesn't belong in this app's dependency tree at all — it's pulled in only because `expo-router` lists `react-native-reanimated` as an *optional* peer, and pnpm's workspace resolution satisfies that peer workspace-wide using `apps/certxa-terminal`'s real `react-native-reanimated@4.5.0` (a different, RN-0.86 app) even for apps that never asked for it. Fixed via `apps/certxa-owner/react-native.config.js`, excluding `react-native-worklets` from iOS/Android autolinking so CocoaPods never evaluates its podspec (kept the npm package itself installed, since Metro/babel still needs to resolve its plugin file). Full history in `pre-errors.md`. Confirmed this got the build past "Install pods" on the next attempt — it then hit the entitlement error above instead, so this fix is validated as far as that boundary.

**Current blocker (unresolved as of 2026-09-24, separate from the above):** a build (`1.0.0 (1)`) was successfully uploaded to App Store Connect and added to an Internal Testing group, but the TestFlight app on the test iPhone still shows the generic "Redeem Code / Invitation Code" screen instead of picking up the build. Likely cause not yet confirmed — leading theory is an Apple ID mismatch between the iPhone's signed-in App Store account and the email added as an internal tester (internal testers must first be added as a **User** under App Store Connect's "Users and Access" before they're selectable as a tester — a separate step from External testing, which accepts any email directly). Also note: a build submitted while an **External** testing group is attached goes to Apple's Beta App Review ("Waiting for Review"); Internal-only testing does not require review — use "Remove from Review" if a build gets stuck this way.

## certxa-solo: new sibling native app (as of 2026-09-25)

A second, separate Expo/React Native app, `apps/certxa-solo`, was built for solo/independent professionals (single calendar, own-client booking, a simple built-in POS with Tap to Pay + Stripe M2 reader, no receipt printing) — a genuinely native app (no WebView), unlike `certxa-owner`. Backend: a new stateless-JWT login (`POST /api/solo/login`, `artifacts/api-server/src/routes/solo-mobile.ts` + `lib/soloAuth.ts`) bridged into the existing session-based auth (`middleware/permissions.ts`'s `attachAuthContext`) so every other endpoint (`/api/appointments`, `/api/services`, `/api/customers`, `/api/payments/terminal/*`) works unchanged.

Its EAS/Apple infra setup has not been done yet (no EAS project, no App ID, no entitlement request) — expect to hit the exact same eas-cli limitations and Tap to Pay entitlement propagation delay documented above for certxa-owner when that work starts; this file's certxa-owner findings apply equally here.
